# Investigation

## Objective

The objective of this phase is to investigate the unauthorized user creation and privilege escalation alerts generated by Wazuh, validate whether persistence was established on the endpoint, determine the scope of access gained, and document the findings.

---

# Step 1 – Review the Wazuh Alert (New User Created)

## Objective

Review the alert generated by Wazuh to identify the key indicators associated with the creation of a new local account.

| Field | Value |
|--------|----------|
| Rule ID | 5902 |
| Rule Level | 8 |
| Description | New user added to the system |
| Agent | wazuhagent123-VirtualBox (001) |
| Agent IP | 10.0.2.15 |
| New Username | backdoor_user |
| MITRE ATT&CK | T1136 – Create Account (Persistence) |

### Observation

A new local account, `backdoor_user`, was created on the endpoint. The username does not match any known service or administrative account naming convention, which is a strong indicator of unauthorized account creation intended to provide persistent access.

---

# Step 2 – Review User Creation Logs

## Objective

Validate the account creation event at the OS log level.

Run:

```bash
sudo grep "useradd" /var/log/auth.log
```

or

```bash
sudo journalctl | grep useradd
```

###  Output

```text
Jul 30 18:44:00 wazuhagent123-VirtualBox useradd[12006]: new user: name=backdoor_user, UID=1001, GID=1001, home=/home/backdoor_user, shell=/bin/bash, from=/dev/pts/1
```

### Observation

The log confirms the account was created interactively from a local terminal rather than by an automated provisioning process. This indicates the account was created manually by a user with shell access to the system, consistent with post-compromise activity following the earlier SSH brute-force attempts.

---

# Step 3 – Review the Wazuh Alert (Privilege Escalation)

## Objective

Review the alert generated by Wazuh indicating that the newly created account was escalated to a privileged group.

| Field | Value |
|--------|----------|
| Rule ID | 100003 (custom rule) |
| Rule Level | 12 |
| Description | Privilege escalation: User added to sudo group using usermod |
| Rule Groups | local, syslog, sshd, account_change, privilege_escalation, persistence |
| Agent | wazuhagent123-VirtualBox (001) |
| Agent IP | 10.0.2.15 |
| Account Affected | backdoor_user |
| MITRE ATT&CK | T1098 – Account Manipulation (Persistence) |
| Decoder | auditd |
| Log Source | /var/log/audit/audit.log |

### Observation

The alert level (12) is significantly higher than the account creation alert (8), reflecting the increased severity of granting elevated privileges to a suspicious account. This is the critical pivot point in the attack chain — the account is no longer just present on the system, it now has administrative capability.

---



# Step 4 – Verify Group Membership

## Objective

Confirm whether `backdoor_user` currently holds elevated (sudo) privileges.

Run:

```bash
id backdoor_user
getent group sudo
```

### Example Output

```text
uid=1001(backdoor_user) gid=1001(backdoor_user) groups=1001(backdoor_user),27(sudo)
sudo:x:27:wazuhagent123,backdoor_user
```

### Observation

`backdoor_user` is confirmed as a member of the `sudo` group, verifying that the privilege escalation alert reflects an actual change in system state and not a false positive.

---

# Step 5 – Check Active Sessions

## Objective

Determine whether `backdoor_user` currently has an active session on the endpoint.

Run:

```bash
who
last backdoor_user
```

### Observation

Document whether `backdoor_user` has logged in via SSH or console since the account was created, and whether any session is currently active. An active session at this stage would indicate the attacker is actively using the backdoor account rather than having merely staged it.

# Analyst Assessment

The investigation identified the creation of a local account, `backdoor_user`, followed shortly after by escalation of that account to the `sudo` group. Both events originated from the same endpoint and terminal session, and occurred approximately 43 seconds apart — consistent with a single, deliberate post-compromise action rather than routine administrative activity.

Unlike the preceding SSH brute-force alert, this activity represents a **successful** stage of the attack: the account was actually created and actually granted elevated privileges, as confirmed by direct verification of group membership (`getent group sudo`). This significantly increases the severity of the incident, since the  simulated attacker now has a standing, privileged account that does not depend on continued exploitation of the original vulnerability.

- Wazuh Alert (Rule 100003 – Privilege Escalation)
- `/var/log/auth.log` (useradd event)
- Group membership verification (`id`, `getent group sudo`)
- Active session check (`who`, `last`)
- Alert metadata and MITRE ATT&CK mapping

---

# Recommended Remediation

1. Disable or lock `backdoor_user` immediately: `sudo usermod -L backdoor_user`
2. Remove the account from the `sudo` group: `sudo deluser backdoor_user sudo`
3. Review shell history and any files owned by `backdoor_user` for further indicators of compromise
4. Consider account deletion once forensic evidence is preserved: `sudo deluser --remove-home backdoor_user`

---

# Conclusion

The investigation confirmed that Wazuh successfully detected both the creation of an unauthorized local account and its subsequent escalation to the `sudo` group. Correlating the alert data with `/var/log/auth.log`, `/var/log/audit/audit.log`, and direct group-membership verification confirmed that the activity was real and successful — unlike the earlier SSH brute-force attempt, which failed to gain access.

This represents a successful persistence and privilege escalation event (MITRE ATT&CK T1136 / T1098) requiring immediate remediation of the `backdoor_user` account.
